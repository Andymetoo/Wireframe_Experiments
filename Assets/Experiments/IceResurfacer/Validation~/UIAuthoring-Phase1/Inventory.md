# Aurora UI inventory: source audit before Phase 1 migration

Audit date: 2026-11-06. Scope: current experiment source, manifest/package cache, authored/procedural scenes and existing prefabs. Historical `Backups~` and `Validation~` copies were excluded from implementation findings. This inventory records the existing interface; Phase 1 changes are documented separately in `Documentation/UI-Authoring-Infrastructure.md`.

## Existing architecture

`IceResurfacerGame.OnGUI()` delegates to the ordinary C# `IceDashboard` object. It is not a persistent Unity component. `IceDashboard.Draw()` applies a uniformly scaled, centered 1600 x 900 GUI matrix with minimum width/height fit. All dashboard rectangles, labels, buttons, colors and sizes are authored in C#. `PointerOverInterface()` independently reproduces panel areas to prevent physical machinery picking, including the whole top header rectangle `(408,24,1164,108)`.

The top header consists of `Header()`, `ConditionerStatus()` and `BladeContactMm()`. The legacy `Meter()` function currently draws a caption and numeric reading; its value argument does not render a fill bar. Adding an editable fill image demonstrates a capability absent from the existing header without changing the underlying state source.

`IceUITheme` is a static IMGUI helper with fixed `Color` fields, GUI styles based on the current built-in skin, and generated five-pixel nine-slice button textures. The textures are `HideAndDontSave` objects; they are not editable imported assets. No screen UI Canvas, RectTransform hierarchy, EventSystem, UI prefab or UI Toolkit document was found in the audited experiment assets. Existing persistent prefabs describe the machine and arena. World-space `TextMesh` labels, such as the service-station tank repeater, are part of that authored machinery/environment and should not be replaced by this screen HUD migration.

Installed packages already include `com.unity.ugui` 2.0.0 and `com.unity.inputsystem` 1.19.0. The cached uGUI package supplies `UnityEngine.UI`, `Unity.TextMeshPro`, TMP editor tools and `Package Resources/TMP Essential Resources.unitypackage`. No font files, TMP font assets or TMP Settings were found in current project Assets during the initial audit. Runtime assembly references initially included only `Unity.InputSystem`; uGUI/TMP consumers will require the corresponding assembly references. No new package is necessary.

## Interaction and visibility constraints

- `IceDashboard.Draw()` gives route manager first ownership, then help, finished/start session sheets, then pause. Those full-screen panels return before drawing any header. `HudHidden` suppresses the live dashboard; Numpad 1 clears relevant transient panels, releases controls/look and updates overlays. Match those states rather than merely checking `Started`.
- The header is normally drawn on foot and during held quicklook. Surface survey, expanded/compact console and GPS elements have additional separate quicklook/on-foot conditions. Suppressing only `Header()` avoids accidentally hiding those unrelated systems.
- `IcePhysicalControls.UpdateInput(enabled, pointerOverHud)` uses that flag only when acquiring a physical control. An ongoing physical drag keeps its owner until release; do not cancel it merely because the pointer later crosses a UI graphic.
- The game currently polls mouse and keyboard through the Input System. Physical picking occurs during the game Update, which may precede the EventSystem update. A current-position GraphicRaycaster query is safer for click-through protection than trusting the previous frame's pointer-over cache.
- `UpdateLook()` captures and hides the cursor while RMB is held, discards acquisition deltas, and restores/warps the original cursor on release. The authored load button must not act during this ownership. Keyboard driving and existing shortcuts should not be consumed by an unnecessary UI navigation action map.
- The existing load click calls `game.ToggleDiagnostics()`. Its original tooltip describes load/acceleration and F3; keep a discoverable hint on the authored counterpart. The new widget hit target must follow its RectTransform. Remove only the obsolete header hit rectangle when the replacement owns the header.
- Noninteractive decorative child graphics should default to `raycastTarget = false`. A visible panel/widget background can explicitly block machine picking where desired. A full-screen layout root should not itself become a raycast target.

## Recommended migration order after the pilot succeeds

1. Bottom status/navigation strip plus notifications/history. These reuse text and button templates, establish editable action rows and message-row prefabs, and cover everyday UI without introducing hydraulic drag semantics.
2. Pause/settings/help, welcome and results. Establish modal focus/visibility ownership, slider binding, and reusable report rows before moving more complex runtime lists.
3. Surface survey and GPS advisory card. Preserve the existing treatment texture and coordinate calculations inside an editable viewport; expose legend and tooltip layouts independently.
4. Route manager and saved-route rows, then advanced recording/training panes. Reuse confirmed modal/list/input patterns; keep storage/recording/fit code and existing route data intact.
5. Compact and expanded machinery console. Reuse all established styling but explicitly validate press/drag/release, lost-device/focus, RMB handoff, keyboard coexistence and physical-control interactions before removing legacy rectangles.
6. On-foot service screen and remaining diagnostics. Reuse status templates while preserving physical water-service behavior; migrate diagnostic text last and keep world-space technical overlays code-driven.

Each subsequent module should own an explicit legacy suppression flag and replace only its own pointer regions after its authored replacement is verified. Do not remove the procedural scene's fallback until an equivalent migration is intentionally supplied there.
