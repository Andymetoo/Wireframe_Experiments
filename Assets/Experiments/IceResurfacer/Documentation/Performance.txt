AURORA R-54 / MEASURED PERFORMANCE
28 October 2026

Historical operator-freedom performance snapshot. SurfaceServiceRefinement.txt
contains the current refinement and its new measurement status. The figures
below describe the preceding implementation; they do not measure the current
5 cm surface field, new rendering response or nose-in service layout.

Scope and status
This report compares the captured previous implementation with the completed
operator-freedom pass using explicit rendered-workload development players.
The final workload comparison records substantially lower measured CPU work at
both resolutions. Full-HUD resurfacing mean frame intervals change from 8.860 to
3.093 ms at 1366x768 and 8.715 to 3.867 ms at 1920x1080. Allocation changes are
mixed, and the 1920x1080 GPU timing is essentially unchanged. These are hidden
fixed-workload results with the limits below. The extended run records bounded
sampled heap but variable, sometimes higher frame costs; it does not prove
indefinite stability. Only the final after/endurance reports are used here.

Environment and method
Windows 11 (10.0.26200), Intel Core i5-11400H at 2.70 GHz, NVIDIA GeForce RTX 3050
Laptop GPU, Unity 6000.4.1f1, Direct3D11, Windows development Mono player.
VSync is off and application target frame rate is unlimited. The owned player
window is hidden/offscreen; the user's open Editor and project settings are
unchanged. Both 1366x768 and 1920x1080 are measured separately.

The benchmark advances one deterministic 20 ms simulation tick per rendered
frame, with live machinery, ice, snow, water, hose effects and IMGUI. Thus FPS
means throughput for this fixed workload: simulation time may advance faster
than wall time. These are not normal real-time gameplay FPS, Editor FPS, or
focused-window input-latency measurements. Different arena geometry, lighting
and HUD between revisions are part of the full-pass comparison; this is not
an isolated single-optimization A/B test.

Each ordinary scenario has 90 warmup frames and a 300-frame measurement budget.
The collector's strict boundary records 299 frame intervals. The normal long
scenario budgets 1500 frames and records 1499 intervals. Fixture setup seeds
positions or tank stock to produce reproducible loads. Driving fixtures can
restart their profiling lane; unlike the separate full gameplay route, these
performance fixtures are not demonstrations of a completed manual run.

Mean_frame and p95_frame cover the whole rendered player loop. CPU_work times
the explicit simulation tick, machine effects, service presentation and periodic
surface/report update. It excludes keyboard/mouse input polling, IMGUI, rendering
and GPU work. The added on-foot movement scenario includes the real movement
collision/camera routines inside CPU_work. GPU time averages only positive
FrameTiming samples; unavailable data must remain unavailable. Draw calls are
-1 in the supplied baseline because that recorder is unavailable, not because
the scene renders no draws.

Whole-frame GC allocation uses the Unity profiler recorder. The separate
GC.GetAllocatedBytesForCurrentThread work counter reports zero in these Mono
player samples; that is not proof of zero allocations. Whole-frame measurements
show substantial nonzero allocation, including IMGUI and instrumentation.
GC collections are generation-zero counter deltas. Managed growth is a live-heap
delta between scenario setup and completion, including warmup and garbage still
awaiting collection; negative growth is possible and does not prove leak freedom.

The service_walking name is retained for the matched baseline service/camera
fixture. It does not execute walking movement. The final on_foot_movement
scenario additionally calls the actual collision-aware MoveFoot/ApplyFootCamera
routines. It has no old counterpart, so no before/after speedup is assigned.

Optimization findings
The former survey path regenerated channels for all 156000 grid samples even
when no ice changed. The new IceField records changed indices in fixed arrays;
cut/snow/finish/process/map channels refresh only affected cells, active wet
cells drive fading, and unchanged process/map textures skip uploads. Physical
surface-score totals are cached by revision. Time and live handling/misuse
values remain current. These changes target measured CPU work without reducing
the grid resolution or substituting a cosmetic trail for real processing.

Snow and water effects remain in bounded particle pools. The hose route reuses
six graph nodes and its buffers. Persistent ground water/snow use two bounded
meshes, refreshed at 5 Hz only when material revisions change. There are no
per-cell scene objects, per-frame creation of mesh objects, or growing lists of
spill particles. FPS and cached performance readouts update at 4 Hz. The rest
of the IMGUI machinery/diagnostic text still renders through the existing UI.

This pass adds geometry, inboard controls, room lights, film/recovery state and
diagnostic/UI content. Lower CPU_work alone would not prove lower whole-frame
cost, lower GPU cost or lower allocation. Here the recorded frame intervals also
improve, but allocation is mixed and the active 1920x1080 GPU cost is unchanged.
Full-HUD allocation remains roughly 17-19 KB per frame in the final active
samples. Periodic collections and remaining frame spikes still merit targeted
IMGUI/profiler work; the independent work API's zero is not an allocation fix.

Diagnostics and remaining limits
F4 toggles the smoothed FPS/frame-time overlay, visible by default. F3 adds
measured simulation/view CPU work, GPU time when available, whole-frame GC and
available draw counts. Machine load and drive causes are separate from CPU load.

FPS labels visible inside HUD-*.png are NOT these performance measurements.
Those screenshots come from the native input/layout probe, which performs
synchronous scripted ticks, ReadPixels captures and automation waits. Its meter
may show a low results-screen rate or a much higher normal-HUD rate because it
is measuring that artificial capture cadence. Use the Performance CSVs for the
comparison; normal play's meter measures its own actual rendered cadence. The
fourteen native HUD states passed interaction/layout checks with no measured
text clipping, independently of this performance benchmark.

The native GfxDeviceD3D11Base::PresentFrame presentation warnings do not arrive
through Application.logMessageReceived. Launchers count them independently;
zero managed errors must not be summarized as zero native warnings. The probe
hides the Development Console overlay for clean evidence but retains log output.
Neither these hidden player runs nor the core tests establish focused-window
latency, subjective smoothness, audio comfort or actual Editor performance.

No automatic profiler result replaces a focused Editor/normal-player check with
the user's usual settings. Relevant next manual checks are a sustained ordinary
resurfacing run, aggressive versus calm steering, full versus compact HUD,
repeated service/dump cycles, and camera transitions on the user's display.
